# Backend Security Audit — Wave 2 (2026-06-09)

**Scope:** `apps/worker/`, `signal-notifier/`, protocol coverage
**Branch:** `audit-backend` from `cfd2b00f` (main)
**Prior audit:** 2026-05-18 (197+ findings, ~30 PRs merged since)

---

## Executive Summary

Wave 2 audit found **1 CRITICAL**, **6 HIGH**, **12 MEDIUM**, and **17 LOW** findings across auth, crypto, input validation, rate limiting, webhooks, WebSocket, and the signal-notifier sidecar. The backend has a strong overall security posture — Zod validation on all production routes, parameterized SQL via Drizzle ORM, comprehensive SSRF guards, and well-designed session management. The most urgent fixes are the sigchain hash verification gap, MLS device ownership bypass, and missing webhook replay protection.

---

## CRITICAL

### C1: Sigchain hash not recomputed server-side — payload not bound to hash
**File:** `apps/worker/services/crypto-keys.ts:93-171`

The server verifies `seqNo` continuity, `prevHash` chain linkage, and Ed25519 signature over `link.hash` — but **never recomputes the hash from link content** (linkType, seqNo, payload, prevHash). A malicious client could submit a link with arbitrary payload but a correctly-signed hash that doesn't actually commit to the payload. The hash chain's tamper-detection property is defeated because the hash doesn't provably bind to the payload content.

**Impact:** Third-party auditors cannot trust that sigchain payloads match their hashes. An attacker controlling a user's signing key could sign a hash over different content than what's stored.

**Fix:** Define a canonical hash computation over `(prevHash || linkType || seqNo || canonicalize(payload))` and verify `link.hash` matches before accepting.

## HIGH

### H1: MLS routes lack device ownership verification (4 endpoints)
**File:** `apps/worker/routes/mls.ts:66-210`

None of the MLS routes verify that the `deviceId` parameter belongs to the authenticated user:
- `GET /mls/messages?deviceId=X` — any hub member can fetch-and-delete another device's pending MLS messages
- `POST /mls/key-packages?deviceId=X` — upload malicious key packages under another device's ID
- `POST /mls/commit` and `POST /mls/welcome` — recipient device IDs aren't validated as hub members

**Impact:** Message denial-of-service (drain another device's queue), impersonation via malicious key packages.

**Fix:** Verify `deviceId` belongs to the authenticated user's registered devices. Validate recipient device IDs are active hub members.

### H2: Account lockdown completion lacks `requireFreshAuth`
**File:** `apps/worker/routes/account.ts:45-59`

`POST /api/account/lockdown` correctly requires fresh Schnorr proof, but `POST /api/account/lockdown/complete` does not. A stolen session token could falsely report lockdown completion, causing the client to believe key rotation succeeded.

**Fix:** Add `requireFreshAuth` to `/lockdown/complete`, or validate a lockdown was initiated recently for this user.

### H3: MLS key package upload allows impersonation
**File:** `apps/worker/routes/mls.ts:178-209`

`POST /key-packages` accepts a `deviceId` query param without ownership verification. An attacker could upload key packages for another user's device, enabling MITM on MLS group Welcome flows.

**Fix:** Cross-reference `deviceId` against authenticated user's device registry.

### H4: Plaintext stored as `encryptedContent` for external messaging channels
**File:** `apps/worker/routes/conversations.ts:316`

```typescript
const encryptedContent = body.encryptedContent ?? plaintextForSending ?? ''
```

When sending outbound messages to SMS/WhatsApp/Signal without client-side pre-encryption, the **plaintext message body** is stored in the `encryptedContent` database field. This violates the zero-knowledge property.

**Impact:** All outbound messages to external channels without pre-encryption are server-readable plaintext at rest.

**Fix:** Call `encryptMessageForStorage()` (already exists in `apps/worker/lib/crypto.ts`) before persisting. Discard plaintext after sending via the messaging adapter.

### H5: No webhook replay protection on any endpoint
**File:** `apps/worker/routes/telephony.ts`, `apps/worker/messaging/router.ts`

Neither telephony nor messaging webhook routes use `checkWebhookReplay`. The infrastructure exists (`apps/worker/services/webhook-replay.ts`, `apps/worker/middleware/webhook-auth.ts`) but is **never wired in**. Captured signed webhook payloads can be replayed indefinitely.

**Impact:** Duplicate call records, duplicate message processing, double audit entries.

**Fix:** Apply `checkWebhookReplay` to all webhook endpoints. The PostgreSQL-backed nonce tracking already exists.

### H6: `webhookAuth` middleware defined but never used
**File:** `apps/worker/middleware/webhook-auth.ts`

The comprehensive `webhookAuth` middleware (content-type enforcement + IP allowlisting + replay protection) is never imported anywhere. This means replay protection, IP allowlisting, and content-type enforcement are all absent from webhook routes.

**Fix:** Apply `webhookAuth` (or its individual components) to all webhook ingress routes.

## MEDIUM

### M1: Rate limiter fails open on database error
**File:** `apps/worker/middleware/rate-limit.ts:77-78`

When the PostgreSQL rate limit check throws (DB outage), requests are allowed through. A database outage disables all rate limiting.

**Fix:** Add in-memory fallback rate limiter for `strict` tier (auth endpoints), or fail closed for auth-related rate limits.

### M2: Rate limiting disabled entirely in development mode
**File:** `apps/worker/middleware/rate-limit.ts:47-49`

All rate limiting skipped when `ENVIRONMENT=development`. Misconfigured staging environments get zero rate protection.

**Fix:** Use a dedicated `DISABLE_RATE_LIMITS=true` flag instead of environment name.

### M3: IP-based rate limiting spoofable without reverse proxy
**File:** `apps/worker/middleware/rate-limit.ts:23-27`

`extractIp` trusts `CF-Connecting-IP` and `X-Forwarded-For` headers directly. Without Cloudflare Tunnels or a trusted proxy, any client can set these headers to bypass IP rate limits.

**Same pattern in:** `apps/worker/routes/auth.ts:43`, `apps/worker/routes/invites.ts:41`, `apps/worker/routes/webauthn.ts:39`.

**Fix:** Validate that forwarded headers come from trusted upstreams, or use connection remote address as fallback.

### M4: Public endpoints without rate limiting
**File:** `apps/worker/app.ts:163-204`

Unprotected public endpoints:
- `GET/PATCH /messaging/preferences` — token-validated but no rate limit, brute-forceable
- `GET /ivr-audio/:promptType/:language` — no rate limit, bandwidth exhaustion vector

**Fix:** Apply `strict` or `webhook` rate limit tier.

### M5: No per-connection WebSocket message rate limiting
**File:** `apps/worker/routes/ws.ts:85-161`

Publishing has per-hub-per-kind rate limits, but incoming client messages (subscribe/unsubscribe/ping) have no messages-per-second throttle. Flooding attack possible.

**Fix:** Add per-connection message rate limit (e.g., 60 msg/min).

### M6: Firehose connection read lacks hub-scoping
**File:** `apps/worker/routes/firehose.ts:169-181`

`GET /:id` with `firehose:read` permission retrieves any connection by UUID without verifying it belongs to the caller's hub. Cross-hub data access possible.

**Fix:** Verify returned connection's `hubId` matches caller's hub context.

### M7: Signal notification digest uses inline permission check (wildcard bypass)
**File:** `apps/worker/routes/signal-notification.ts:281-293`

`POST /digest/run` checks `permissions.includes('system:admin')` directly instead of `requirePermission()`. A super-admin with wildcard `*` permission (but not literal `system:admin`) would be denied.

**Fix:** Replace with `requirePermission('system:admin')` middleware.

### M8: Health check leaks error messages to unauthenticated callers
**File:** `apps/worker/routes/health.ts:31,47,68,85`

`err.message` returned in `detail` field for failing health checks. Could leak internal hostnames, connection strings, database errors.

**Fix:** Return generic `'Connection check failed'`. Log actual error server-side.

### M9: Webhook URL falls back to request URL without `WEBHOOK_BASE_URL`
**File:** `apps/worker/lib/webhook-url.ts:18-21`

If `WEBHOOK_BASE_URL` is unconfigured in production, webhook signature validation uses the spoofable `Host` header.

**Fix:** Fail-hard at startup if `WEBHOOK_BASE_URL` is empty in non-development environments.

### M10: SSRF DNS rebinding on telephony provider test
**File:** `apps/worker/routes/settings.ts:484`

Asterisk ARI URL test uses `validateExternalUrl()` (static hostname check) but `safeFetch` without `ssrfGuard: true`. DNS rebinding attack possible.

**Fix:** Use `validateExternalUrlWithDns()` and pass `ssrfGuard: true` to `safeFetch`.

### M11: Three firehose crypto labels missing from canonical crypto-labels.json
**File:** `packages/shared/crypto-labels.ts:124-130`

`LABEL_FIREHOSE_AGENT_SEAL`, `LABEL_FIREHOSE_BUFFER_ENCRYPT`, `LABEL_FIREHOSE_REPORT_WRAP` defined in TS but missing from `packages/protocol/crypto-labels.json`. Won't be generated to Swift/Kotlin.

**Fix:** Add all three to `crypto-labels.json`.

### M12: Signal notifier encryption key derived from API key
**File:** `signal-notifier/src/store.ts:27`, `signal-notifier/src/crypto.ts:10-12`

Encryption key for stored identifiers derived from the bearer token via HKDF. API key rotation makes all stored ciphertext undecryptable. Salt is also derived from the same secret (not ideal per HKDF best practices).

**Fix:** Use a separate, persistent encryption secret. Store salt as configuration value.

## LOW

### L1: DEV_AUTH_BYPASS signature skip — no production guard
**File:** `apps/worker/middleware/auth.ts:35-47`

Dual-condition guard (`ENVIRONMENT=development && DEV_AUTH_BYPASS=true`) skips Ed25519 signature verification. No startup assertion prevents this in production.

**Fix:** Reject `DEV_AUTH_BYPASS=true` at startup when `NODE_ENV=production`.

### L2: ADMIN_PUBKEY auto-restoration of super-admin role
**File:** `apps/worker/middleware/auth.ts:72-86`

ADMIN_PUBKEY user's roles are automatically restored. Cannot be locked out during incident response.

**Fix:** Add kill switch env var (`ADMIN_PUBKEY_AUTO_RESTORE=false`) for incident containment.

### L3: Public OpenAPI spec reveals full API surface
**File:** `apps/worker/app.ts:299-300`

`/api/openapi.json` and `/api/docs` are unauthenticated, revealing every endpoint and schema.

**Fix:** Gate behind auth or restrict to development mode.

### L4: Events routes deprecated but not sunset-enforced
**File:** `apps/worker/routes/events.ts:33-38`

`Sunset: 2026-07-01` header set but no enforcement. Less than a month away.

**Fix:** Implement 410 Gone enforcement after sunset date.

### L5: PUK GET lacks device ownership verification
**File:** `apps/worker/routes/puk.ts:51-129`

`GET /envelopes/:deviceId` doesn't verify the device belongs to the authenticated user.

**Fix:** Cross-reference deviceId against caller's registered devices.

### L6: Conversations/records/reports routes rely on inline access checks
**Files:** `apps/worker/routes/conversations.ts`, `apps/worker/routes/records.ts`, `apps/worker/routes/reports.ts`

No top-level `requirePermission()` middleware. Access control scattered across inline checks, increasing risk of omission.

**Fix:** Add base permission guards with additional inline checks layered on top.

### L7: Dev route handlers use `c.req.json()` without Zod validation
**File:** `apps/worker/routes/dev.ts` (lines 153, 205, 235, 286, 704, 754, etc.)

Most dev/simulation endpoints use `await c.req.json()` with `as` casts. Triple-gated (environment + secret + guard) but inconsistent with production patterns.

**Fix:** Use Zod validation even for dev-only endpoints.

### L8: `provider-setup.ts` DELETE body unvalidated
**File:** `apps/worker/routes/provider-setup.ts:917`

Raw JSON body fallback for `registrationId` without Zod validation.

**Fix:** Add Zod schema for the optional body.

### L9: IVR audio path params not validated
**File:** `apps/worker/routes/settings.ts:665-695`

`promptType` and `language` URL params passed to service without allowlist validation.

**Fix:** Validate against known prompt types and ISO language codes.

### L10: Auth login rate limit falls back to 'unknown'
**File:** `apps/worker/routes/auth.ts:43`

Uses only `CF-Connecting-IP`, not the `extractIp` helper. Without Cloudflare, all logins share one rate limit bucket.

**Fix:** Use `extractIp` helper for consistency.

### L11: No WebSocket connection limit per user
**File:** `apps/worker/routes/ws.ts`, `apps/worker/lib/ws-manager.ts`

No cap on simultaneous WebSocket connections per pubkey. Memory exhaustion vector.

**Fix:** Cap at ~10 connections per pubkey.

### L12: Webhook IP allowlist only supports IPv4
**File:** `apps/worker/middleware/webhook-ip-allowlist.ts:7-13`

`ipToNum` only handles IPv4. IPv6 addresses cause incorrect CIDR matching.

**Fix:** Add IPv6 support or reject IPv6 before matching.

### L13: Signal notifier health endpoint leaks error messages
**File:** `signal-notifier/src/index.ts:75-85`

Unauthenticated `/health` returns `err.message` on failure.

**Fix:** Return only `{ ok: false }` in production.

### L14: No SSL enforcement in database connection config
**File:** `apps/worker/db/index.ts:24-37`

No explicit SSL configuration. Relies on `DATABASE_URL` containing `?sslmode=require`.

**Fix:** Enforce SSL in connection config for production.

### L15: Signal notifier DB lacks schema isolation
**File:** `signal-notifier/src/db/connection.ts`

Creates tables in the default schema alongside main app tables. Compromised sidecar could access app tables.

**Fix:** Use dedicated PostgreSQL schema and restricted DB role.

### L16: Audit LIKE search allows wildcard injection
**File:** `apps/worker/services/audit.ts:253-259`

Admin-only search parameter used in LIKE pattern without escaping `%` and `_`.

**Fix:** Escape wildcards in user-supplied search strings.

### L17: Protocol spec LABEL_CONTACT_ID value mismatch
**File:** `docs/protocol/PROTOCOL.md:220`

Spec says `llamenos:contact-id`, code uses `llamenos:contact-identifier`.

**Fix:** Update PROTOCOL.md to match code.

## Positive Findings

These areas are well-implemented and deserve recognition:

- **Session management:** Token rotation, Ed25519 replay protection, 5-min freshness, Schnorr fresh-auth for sensitive ops
- **Zod validation:** All production routes use `validator('json', schema)` — no raw body access
- **SQL safety:** Drizzle ORM with parameterized queries throughout — zero SQL injection surface
- **SSRF guard:** Comprehensive private IP range blocking, DNS rebinding protection available
- **Webhook signatures:** Telephony and messaging webhooks validate provider signatures
- **Call tokens:** Opaque, single-use (delete-on-read), hub ID resolved from DB (not URL params)
- **Upload safety:** UUID-only storage keys — no user-controlled filenames in paths
- **Error handling:** Global handler returns generic 500 for unexpected errors, logs stack traces server-side
- **Audit chain:** Serialized writes via `SELECT ... FOR UPDATE`, comprehensive chain verification
- **WS auth:** Ed25519 challenge-response with 10s timeout, 5-min membership revalidation
- **Signal notifier:** Timing-safe token comparison, HMAC registration tokens, rate limiting, PII redaction
- **Key zeroing:** Agent identity nsec bytes zeroed after use
- **Logger redaction:** Sensitive patterns (nsec, hex keys, phone numbers, emails) redacted
