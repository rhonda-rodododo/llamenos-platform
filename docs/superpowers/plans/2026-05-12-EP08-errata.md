# EP08 Cross-Plan Review Errata

**Date:** 2026-05-12
**Reviewer:** Supervisor (cross-plan consistency check)
**Plans reviewed:** P1 (backend), P2 (crypto), P3 (desktop), P4 (mobile + i18n)

## Findings

### E1: Duplicate crypto label task (P1 Task 2 + P2 Task 1) — CONFLICT

Both P1 Task 2 and P2 Task 1 add `LABEL_AUDIT_USER_KEY_WRAP` and `LABEL_ERASURE_OVERRIDE_SIG` to `packages/protocol/crypto-labels.json`.

**Resolution:** P2 is the authoritative plan for crypto changes. Skip P1 Task 2 entirely — P2 Task 1 covers it. P1 Task 2 should be marked as "covered by P2" by the executing agent. If P1 executes before P2, P1 Task 2 can run; P2 Task 1 will be a no-op (labels already present).

### E2: Spec says XChaCha20-Poly1305 for audit keys — CORRECTED in plans

The spec (Section 3) references "XChaCha20-Poly1305" for audit user key encryption. The crypto crate only has AES-256-GCM. P2 correctly uses AES-256-GCM via HPKE. The spec should be updated to say AES-256-GCM.

**Resolution:** Update spec Section 3 to reference AES-256-GCM (not XChaCha20-Poly1305). Non-blocking — plans are already correct.

### E3: P4 has 102 i18n keys vs spec's ~67 estimate — ACCEPTABLE

P4 Task 1 adds 102 leaf keys (spec estimated ~67). The increase is due to thorough coverage of confirmation dialogs, countdown variants, and admin queue states. This is fine — more strings is better than missing strings.

**Resolution:** No action needed. Update spec estimate if desired.

### E4: Execution order dependency — NOTED

P2 (crypto) should execute before or in parallel with P1 (backend), because P1's ErasureService needs the Rust crypto functions from P2 for audit key operations and signature verification. However, P1 can stub these calls initially and wire them later.

P3 (desktop) and P4 (mobile + i18n) depend on P1 routes existing (or being mocked). P4's i18n task (Task 1) has no dependencies and should execute first.

**Recommended execution order:**
1. P4 Task 1 (i18n) + P2 (crypto) — in parallel, no dependencies
2. P1 (backend) — depends on P2 labels being in place
3. P3 (desktop) + P4 Tasks 2-10 (mobile views) — in parallel, depend on P1 routes

### E5: Spec audit log `details` field encryption — MIGRATION GAP

Spec Section 3 says existing audit entries with plaintext `details` get `details` set to `null` on erasure. But P1's erasure cascade only replaces `actorPubkey` with `[erased]` and sets `erasedAt`. The plaintext `details` scrubbing for pre-EP08 entries needs to be in the cascade.

**Resolution:** P1's ErasureService cascade should include: `UPDATE audit_log SET details = NULL, actorPubkey = '[erased]', erasedAt = NOW() WHERE actorPubkey = $1 AND erasedAt IS NULL`. Executing agents should verify this is covered.

### E6: `erasedAt` column addition — covered but verify migration

P1 adds `erasedAt` to the `audit_log` table in the Drizzle schema. The migration (P1 Task 19) should include this column. Verify the Drizzle migration generator picks it up.

**Resolution:** Executing agent should verify after running `bunx drizzle-kit generate`.
