## Executive Summary

The Android client demonstrates strong security architecture. Device key material is held exclusively in Rust/JNI memory, all storage uses EncryptedSharedPreferences with hardware-backed MasterKeys, cert pinning is dual-layer (OS + OkHttp), and deep links are validated against an explicit allowlist. Prior audit findings (PIN brute-force, deep link injection, nsec in ViewModel) have been addressed.

**Critical findings: 0**
**High findings: 2**
**Medium findings: 5**
**Low findings: 6**
**Informational: 4**

## 1. Keystore / EncryptedSharedPreferences

### Status: STRONG

- **MasterKey**: AES-256-GCM with StrongBox request, graceful TEE fallback (`KeystoreService.kt:59-70`).
- **EncryptedSharedPreferences**: Key encryption via AES256-SIV, value encryption via AES256-GCM (`KeystoreService.kt:73-81`).
- **Biometric key**: Separate AndroidKeyStore AES-256-GCM key with `setUserAuthenticationRequired(true)` and `setInvalidatedByBiometricEnrollment(true)`. StrongBox requested with fallback (`KeystoreService.kt:273-311`).
- **Wake key**: Separate AndroidKeyStore AES-256-GCM key for push notification decryption without PIN. StrongBox requested (`WakeKeyService.kt:110-166`).
- **allowBackup="false"**: Set in AndroidManifest.xml (line 27). Prevents backup extraction of encrypted preferences.
- **PIN lockout**: Escalating schedule (30s → 2m → 10m → wipe at 10 attempts). State stored in encrypted preferences (`KeystoreService.kt:145-201`).

### Findings

**(L01) LOW — Lockout timestamp bypass via clock manipulation**
`KeystoreService.kt:151` compares `System.currentTimeMillis()` against the lockout timestamp. A user with ADB access could set the clock forward to bypass lockout. This is acceptable given the threat model (lockout is primarily against physical shoulder-surfing, not forensic extraction), but documenting the limitation is worthwhile.

**(L02) LOW — CrashReporter uses separate EncryptedSharedPreferences instance**
`CrashReporter.kt:48-74` creates its own MasterKey and EncryptedSharedPreferences (`crash_reporter_prefs`). This is correct (separate key, separate file), but the StrongBox fallback pattern is duplicated. Minor code hygiene issue.

## 2. JNI Crypto Boundary

### Status: STRONG

- **All crypto operations route through Rust FFI** (`org.llamenos.core.*` functions).
- Device private keys NEVER enter JVM memory — `CryptoService.kt` only holds public keys (`signingPubkeyHex`, `encryptionPubkeyHex`).
- Hub keys stored exclusively in Rust (`mobileSetHubKey`), server event keys in Rust (`mobileSetServerEventKeys`).
- HPKE seal/open, symmetric encrypt/decrypt, auth token signing, Shamir operations, sigchain — all delegate to Rust.
- `EphemeralKeypair` implements `AutoCloseable` with secret zeroization (`CryptoService.kt:170-181`).
- `WakeKeyService.storeWakeSecret()` zeroizes input bytes in a `finally` block (`WakeKeyService.kt:165`).

### Findings

**(M01) MEDIUM — WakeKeyService.getOrCreateWakePublicKey() leaves secretKeyHex in JVM memory**
`WakeKeyService.kt:82-85`: The `secretKeyHex` String is generated by FFI, then converted to `ByteArray` for storage. The String is immutable and cannot be zeroized — it will persist in JVM heap until GC. The `secretBytes` array IS zeroized (via `storeWakeSecret`), but the hex String lingers.

**Recommendation:** Have the Rust FFI return bytes directly instead of a hex string, or immediately store and let the String go out of scope (already happens, but worth noting the inherent limitation).

**(M02) MEDIUM — CryptoService.generateEphemeralKeypair() also has hex String in JVM**
`CryptoService.kt:747-752`: Similar pattern — `secretKeyHex` is a String from FFI that cannot be zeroized. The `EphemeralKeypair.secretBytes` is properly zeroized on `close()`, but the source hex String remains in heap.

**(I01) INFO — testHubKeys ConcurrentHashMap is JVM-only test fallback**
`CryptoService.kt:803`: The `testHubKeys` map holds hub keys in JVM memory, but only when `nativeLibLoaded` is false (test-only path). No production risk.

## 3. Network Security Config

### Status: STRONG

- **Release** (`main/res/xml/network_security_config.xml`): `cleartextTrafficPermitted="false"`, certificate pins for ISRG Root X1 (RSA 4096) and X2 (ECDSA P-384) on `*.llamenos.org`, expiry 2027-01-01.
- **Debug** (`debug/res/xml/network_security_config.xml`): Cleartext allowed only for `localhost`, `10.0.2.2`, `192.168.50.95`. No wildcard. No debug trust-anchors (`<certificates src="user" />` is absent — good).
- **OkHttp CertificatePinner** (`ApiService.kt:86-117`): Dual Let's Encrypt root CA pins, hard-fail mode. Dynamically configured per hub hostname. Localhost exempted for development only.
- **WebSocket** (`WebSocketService.kt:124-131`): Refuses non-HTTPS hub URLs in release builds. `BuildConfig.DEBUG` gates HTTP→ws:// for local dev.

### Findings

**(L03) LOW — Debug network config has hardcoded LAN IP**
`debug/network_security_config.xml:22`: `192.168.50.95` is hardcoded. This is debug-only and has `includeSubdomains="true"`, which is fine for a single LAN address but could be cleaner as a range comment.

**(I02) INFO — Certificate pin expiry 2027-01-01**
Pin-set expiration is ~6 months away. Needs a calendar reminder for renewal. The ISRG roots themselves expire 2035/2040.

## 4. Deep Link Handling

### Status: STRONG

- **Allowlist-based validation**: `DeepLinkValidator.isAllowed()` checks scheme (`llamenos`) and host against `ALLOWED_HOSTS = {"oauth", "call", "hub"}`.
- **User confirmation for sensitive actions**: Hub switching requires an AlertDialog confirmation (`DeepLinkActivity.kt:50-54`).
- **Relay URL injection defense**: `relayUrl` parameter is validated against the configured hub URL via `RelayUrlValidator.isValidRelayUrl()`, which enforces `wss://`/`https://` scheme, public host check (blocks loopback, RFC 1918, link-local), and domain match (`RelayUrlValidator.kt:43-49`).
- **OAuth CSRF protection**: 32-byte `SecureRandom` state parameter with server-side validation (`DeepLinkActivity.kt:127-138`).
- **MainActivity deep links**: `parseDeepLink()` has its own allowlist of hosts (cases, notes, calls, etc.) — separate from `DeepLinkActivity`.

### Findings

**(L04) LOW — DeepLinkActivity logs callId and hubId at DEBUG level**
`DeepLinkActivity.kt:83,110`: `Log.d(TAG, "Call deep link: callId=$callId")` and `"Hub deep link: hubId=$hubId"`. While call IDs and hub IDs are not PII, they are operational metadata that could aid correlation attacks if logcat is accessible. These are DEBUG level (stripped by ProGuard in release? — see §10).

## 6. Export / Content Provider Exposure

### Status: GOOD

- **Exported components**:
  - `MainActivity` — exported (LAUNCHER). Intent filter limited to `MAIN/LAUNCHER`.
  - `DeepLinkActivity` — exported (deep links). `noHistory="true"`, `excludeFromRecents="true"`. Narrow intent filters (specific scheme+host+path combinations).
  - `PushService` (BroadcastReceiver) — exported for UnifiedPush intents. Standard UP action filters.
  - `CoreService` (Linphone) — `exported="false"`.

- **No ContentProviders**: No `<provider>` in the manifest. No `FileProvider` either (which is fine for now — file sharing isn't implemented).

### Findings

**(H01) HIGH — PushService receiver is exported without permission protection**
`AndroidManifest.xml:77-86`: The `PushService` BroadcastReceiver is `exported="true"` but has no `android:permission` attribute. Any app on the device can send fake `org.unifiedpush.android.connector.MESSAGE` broadcasts with arbitrary payloads. While the payload is encrypted (HPKE envelope), a malicious app could:
1. Send garbage payloads causing unnecessary decryption attempts
2. Send valid-looking JSON with `"type": "incoming_call"` triggering fake call notifications (the VoIP push path at `PushService.kt:154` does NOT decrypt — it shows a notification based on unverified fields)

**Recommendation:** Add `android:permission="org.unifiedpush.android.connector.SEND_PUSH"` or a custom signature-level permission to restrict who can send to this receiver. Alternatively, verify that UnifiedPush SDK v3 handles this internally.

## 7. Protocol Compliance

### Status: MOSTLY COMPLIANT

The Android client implements core protocol features correctly:
- **HPKE envelope format** with version 3, label IDs, domain separation labels from `CryptoLabels`
- **Per-note forward secrecy** with random symmetric key + HPKE-wrapped envelopes
- **Per-message forward secrecy** with same pattern, using `LABEL_MESSAGE`
- **Per-device keys** (Ed25519 signing + X25519 encryption) — no nsec
- **PUK (Per-User Key)** creation, rotation (CLKR), seed unwrapping
- **Sigchain** creation, single-link verification, full chain verification
- **Hub key distribution** — HPKE unwrap with `LABEL_HUB_KEY_WRAP`, Rust-only storage
- **Server event encryption** — XChaCha20-Poly1305 with epoch rotation
- **File encryption** — per-recipient HPKE with `LABEL_FILE_KEY` and `LABEL_FILE_METADATA`
- **Call metadata E2EE** — `LABEL_CALL_META` envelopes
- **Draft encryption** — hub key + HKDF-derived draft key
- **Shamir secret sharing** for recovery groups
- **Auth tokens** — Ed25519 signed with nonce + timestamp

### Findings

**(H02) HIGH — DeviceLinkViewModel uses mock ECDH, not real relay protocol**
`DeviceLinkViewModel.kt:120-148`: The device linking flow is mocked — it generates a random "desktop" public key instead of connecting to a real provisioning relay. This means multi-device linking is non-functional. The crypto primitives (ECDH, SAS code) are real, but the transport layer is missing.

**(M03) MEDIUM — RecipientEnvelope in encryptMessage lacks v/labelId fields**
`CryptoService.kt:488-494`: Message encryption creates `RecipientEnvelope(pubkey, enc, ct)` — a protocol type from codegen. The `HpkeEnvelope(v, labelId, enc, ct)` wrapper is used internally but the final envelope sent to the server may not carry the version and label ID. Need to verify this matches the server's expectation for message envelopes.

## 8. Missing Features

**(M04) MEDIUM — Device linking is mock-only** (same as H02 above)
The QR scan flow exists (`DeviceLinkScreen.kt` with CameraX + ML Kit), but the WebSocket provisioning relay connection is not implemented.

**(M05) MEDIUM — SFrame voice E2EE not implemented**
The protocol specifies SFrame for encrypted voice media. `LinphoneService.kt` handles SIP/VoIP via Linphone SDK but does not integrate with `packages/crypto` for SFrame key derivation. Voice calls are encrypted by Linphone's SRTP but not with the app's E2EE key material.

**(I03) INFO — Transcription service is a UI shell**
`TranscriptionService.kt` exists but appears to be a placeholder for the WASM Whisper integration (desktop-only feature). Android could potentially use a native ONNX runtime.

**(I04) INFO — EventDetailScreen has placeholder tabs**
`EventDetailScreen.kt:406-440`: Timeline, Linked Cases, and Linked Reports tabs are placeholder composables.

## 10. ProGuard / R8

### Status: GOOD

- **Minification enabled**: `isMinifyEnabled = true` in release build type (`build.gradle.kts:71`).
- **Resource shrinking**: `isShrinkResources = true` (`build.gradle.kts:72`).
- **Crypto classes kept**: JNI native methods, CryptoService fields, UniFFI bindings, all properly kept.
- **Serialization kept**: `@Serializable` classes and their serializers properly kept.
- **Security classes kept**: `EncryptedSharedPreferences`, `MasterKey` explicitly kept.
- **Compose kept**: Lambda group classes and `@Composable` methods kept.

### Findings

**(L06) LOW — ProGuard does not strip Log.d/Log.v in release**
`proguard-rules.pro` does not contain rules to strip debug/verbose logging. Add:
```proguard
-assumenosideeffects class android.util.Log {
    public static int d(...);
    public static int v(...);
}
```
This would eliminate all DEBUG and VERBOSE log calls from the release APK, removing the logcat exposure from §9.

## Positive Observations

1. **Key material isolation** is excellent — device private keys never enter JVM memory.
2. **EncryptedSharedPreferences everywhere** — no plaintext storage found.
3. **StrongBox with graceful fallback** — consistently applied across MasterKey, biometric key, and wake key.
4. **Deep link security** is thorough — allowlist, confirmation dialogs, relay URL validation with domain matching.
5. **allowBackup="false"** prevents backup extraction attacks.
6. **FLAG_SECURE** applied on PIN screens, account recovery, and admin recovery screens.
7. **Dual-layer cert pinning** (OS network_security_config + OkHttp CertificatePinner).
8. **Crash reporter is opt-in** with zero PII in reports.
9. **OAuth CSRF protection** via 32-byte SecureRandom state.
10. **Auto-lock after 5-minute background timeout** (`MainActivity.kt:86-93`).
