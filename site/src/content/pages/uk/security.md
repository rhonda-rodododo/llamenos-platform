## Якщо вашого хостинг-провайдера викликають до суду

| Вони МОЖУТЬ надати | Вони НЕ МОЖУТЬ надати |
|---------------------|------------------------|
| Метадані дзвінків/повідомлень (час, тривалість) | Вміст нотаток, розшифровок, текстів звітів |
| Зашифровані дані з бази даних | Імена волонтерів (наскрізне шифрування) |
| Які облікові записи волонтерів були активні в певний час | Записи довідника контактів (наскрізне шифрування) |
| Записи доставки розсилок | Вміст повідомлень (зашифровано після надходження, зберігається як шифротекст) |
| | Ключі розшифрування (захищені вашим PIN-кодом, вашим обліковим записом постачальника ідентифікації та, за бажанням, апаратним ключем безпеки) |
| | Ключі шифрування окремих нотаток (епемерні — знищуються після обгортання) |
| | Ваш HMAC-секрет для зворотного гешування телефонів |
| | Вміст часток відновлення (зашифровано, сервер не може прочитати) |

**Сервер зберігає дані, які не може прочитати.** Метадані (коли, як довго, які облікові записи) є видимими. Вміст (що було сказано, що було написано, хто ваші контакти) — ні.

## За функціями

Рівень вашої конфіденційності залежить від того, які канали ви ввімкнули:

### Голосові дзвінки

| Якщо ви використовуєте... | Треті сторони можуть отримати доступ | Сервер може отримати доступ | Вміст з наскрізним шифруванням |
|---------------------------|--------------------------------------|-----------------------------|--------------------------------|
| Twilio/SignalWire/Vonage/Plivo | Аудіо дзвінка (в реальному часі), записи дзвінків | Метадані дзвінка | Нотатки, розшифровки |
| Самостійно розміщений Asterisk | Нічого (ви контролюєте його) | Метадані дзвінка | Нотатки, розшифровки |
| Браузер-до-браузера (WebRTC) | Нічого | Метадані дзвінка | Нотатки, розшифровки |

**Повістка постачальнику телефонії**: Вони мають детальні записи дзвінків (час, номери телефонів, тривалість). Вони НЕ мають нотаток або розшифровок дзвінків. Запис вимкнено за замовчуванням.

**Розшифровка**: Розшифровка відбувається повністю у вашому браузері з використанням AI на пристрої. **Аудіо ніколи не залишає ваш пристрій.** Зберігається лише зашифрована розшифровка.

### Текстові повідомлення (один-на-один)

| Канал | Доступ постачальника | Зберігання на сервері | Примітки |
|-------|----------------------|-----------------------|----------|
| SMS | Ваш постачальник телефонії читає всі повідомлення | **Зашифровано** | Постачальник зберігає оригінальні повідомлення |
| WhatsApp | Meta читає всі повідомлення | **Зашифровано** | Постачальник зберігає оригінальні повідомлення |
| Signal | Мережа Signal має наскрізне шифрування; міст перешифровує після надходження | **Зашифровано** | Бажаний маршрут, коли доступний |

**Доставка через Signal у першу чергу**: Якщо отримувач має Signal, повідомлення автоматично маршрутизуються через Signal — ваш постачальник телефонії ніколи не бачить вмісту. Для SMS за замовчуванням надсилається лише загальне сповіщення "у вас нове повідомлення" (без тексту повідомлення), тому журнали вашого постачальника не містять конфіденційного вмісту.

**Повідомлення шифруються в момент надходження на ваш сервер.** Сервер зберігає лише шифротекст. Ваш постачальник телефонії або обміну повідомленнями все ще може мати оригінальне повідомлення — це обмеження цих платформ, яке ми не можемо змінити.

**Повістка постачальнику обміну повідомленнями**: Постачальники SMS мають повний вміст повідомлень, лише якщо ви явно ввімкнули режим повного вмісту SMS. У режимі лише сповіщень за замовчуванням тіла SMS не містять вмісту повідомлень. Meta має вміст WhatsApp. Повідомлення Signal мають наскрізне шифрування до мосту, але міст (що працює на вашому сервері) розшифровує їх перед повторним шифруванням для зберігання. У всіх випадках **ваш сервер має лише шифротекст** — хостинг-провайдер не може прочитати вміст повідомлень.

### Масові та розсилки

Адміністратори можуть надсилати масові повідомлення підписникам через SMS, WhatsApp, Signal або RCS.

**Важливо: вихідні розсилки не мають наскрізного шифрування на сервері.** Щоб доставити повідомлення підписникам SMS або WhatsApp, сервер повинен тимчасово обробити вміст у відкритому тексті та передати його постачальнику обміну повідомленнями. Постачальник потім доставляє його та може зберігати копію.

| Канал | Доступ сервера під час надсилання | Доступ постачальника | Після доставки |
|-------|-----------------------------------|----------------------|----------------|
| SMS розсилка | Відкритий текст (тимчасово, для доставки) | Повний вміст повідомлення | Постачальник зберігає |
| WhatsApp розсилка | Відкритий текст (тимчасово, для доставки) | Повний вміст повідомлення (Meta) | Постачальник зберігає |
| Signal розсилка | Відкритий текст (тимчасово, для доставки) | Наскрізне шифрування через мережу Signal | Не зберігається постачальником |
| RCS розсилка | Відкритий текст (тимчасово, для доставки) | Google може бачити вміст | Постачальник зберігає |

**Що це означає**: Розсилки не повинні містити конфіденційної інформації про абонентів. Використовуйте їх для оголошень, повідомлень про розклад та ресурсів — не для деталей справ або чогось, що може ідентифікувати абонентів чи волонтерів.

Номери телефонів підписників зберігаються як гешовані ідентифікатори — ваша база даних ніколи не містить списку підписників у відкритому тексті. Запити на відписку (STOP) обробляються негайно, а статус підписника оновлюється.

### Нотатки, розшифровки та звіти

Весь вміст, створений волонтерами, має наскрізне шифрування:

- Кожна нотатка використовує **унікальний випадковий ключ** (пряма секретність — компрометація однієї нотатки не компрометує інші)
- Ключі обгортаються окремо для волонтера та кожного адміністратора
- Сервер зберігає лише шифротекст
- Розшифрування відбувається на вашому пристрої, у захищеному шарі, який ніколи не розкриває ключі інтерфейсу користувача застосунку
- **Спеціальні поля, вміст звітів та вкладення файлів шифруються окремо**

**Записи справ та дані сутностей**: Структуровані записи справ (контакти, справи, ланцюжки доказів) використовують ту саму модель шифрування — кожен елемент зашифровано унікальним ключем, обгорнутим для авторизованих переглядачів. Сервер не може читати вміст справи.

**Вилучення пристрою**: Без вашого PIN-коду **та** доступу до вашого облікового запису постачальника ідентифікації, зловмисники отримують зашифрований блок, захищений Argon2id — функцією похідної ключа, стійкою до пам'яті, яка робить атаки грубою силою зі спеціалізованим обладнанням (GPU, ASIC) на порядки дорожчими, ніж традиційні підходи. Якщо ви також використовуєте апаратний ключ безпеки, ваші дані захищають **три незалежні фактори**.

## Ваші пристрої

### Перегляд та відкликання пристроїв

Застосунок веде список усіх пристроїв, з яких ви входили. Ви можете переглянути цей список та відкликати будь-який пристрій, який ви не впізнаєте.

**Коли ви відкликаєте пристрій:**
- Цей пристрій негайно блокується для доступу до вашого облікового запису
- Ваші ключі шифрування змінюються, щоб відкликаний пристрій не міг розшифрувати будь-який майбутній вміст
- Відкликання записується в історію безпеки вашого облікового запису

Це означає, що навіть якщо хтось має копію ваших зашифрованих даних до відкликання, вони не зможуть прочитати новий вміст, створений після відкликання.

### SAS верифікація за допомогою емодзі

Для організацій з високими вимогами безпеки адміністратори можуть перевіряти ідентичність пристрою за допомогою SAS (Short Authentication String) — що відображається як послідовність із 7 емодзі.

**Як це працює:**
1. Адміністратор та власник пристрою порівнюють свої послідовності емодзі (особисто, по телефону або через довірений канал)
2. Якщо емодзі збігаються, пристрій підтверджується як такий, що належить зареєстрованому власнику
3. Верифікація записується — адміністратори можуть бачити, які пристрої були верифіковані

Це захищає від зловмисника, який зареєстрував фальшивий пристрій під чужим обліковим записом. Послідовність емодзі виводиться з криптографічних ідентифікаційних ключів обох пристроїв та одноразового коду — сервер не може маніпулювати або передбачити її.

## Видалення облікового запису

### Самостійне видалення

Ви можете подати запит на остаточне видалення вашого облікового запису та всіх пов'язаних з ним даних. За замовчуванням існує затримка (встановлена адміністратором вашого хабу, зазвичай 72 години) перед завершенням видалення — це дає вам час скасувати, якщо запит було зроблено під примусом.

**Що видаляється:**
- Ключі вашого пристрою (що робить весь зашифрований вміст остаточно нечитабельним, навіть з резервних копій)
- Ваш обліковий запис, призначення ролей та історія змін
- Ваші токени push-сповіщень

**Що відбувається із зашифрованим вмістом, який ви створили**: Нотатки, розшифровки та звіти, автором яких ви є, перешифровуються для інших авторизованих читачів (інших адміністраторів). Ваша копія ключа розшифрування знищується. Сам вміст зберігається для інших авторизованих переглядачів — він не масово видаляється, оскільки абоненти та історія справ належать хабу, а не вам особисто.

**Журнали аудиту**: Ваші записи в журналі аудиту крипто-знищуються — ключ шифрування для кожного користувача знищується, роблячи ваші записи нечитабельними. Ланцюжок гешів (структура доказу недоторканності) залишається недоторканним.

### Екстрене видалення

Якщо ви вважаєте, що ваш обліковий запис знаходиться під безпосередньою загрозою, ви можете подати запит на екстрене видалення з співпідтверджувачем — іншою довіреною особою (адміністратором або довіреним контактом), яка підтверджує терміновість. Це скорочує затримку до мінімум 4 годин. Мінімум у 4 години існує для захисту від примусового видалення (коли вас змушують видалити докази до прибуття допомоги).

### Що неможливо видалити

Метадані дзвінків (хто відповів, коли, як довго) є частиною запису аудиту хабу. Адміністратор вашого хабу контролює, як довго вони зберігаються. Відповідно до GDPR, ви маєте право вимагати виправлення або видалення — зверніться до адміністратора вашого хабу.

## Групи відновлення

Якщо ви втратите всі пристрої (телефон знищено, ноутбук вкрадено, все), ви зазвичай втратите доступ до всіх зашифрованих даних. Групи відновлення вирішують цю проблему.

### Як працює відновлення

Ви призначаєте групу довірених контактів (зазвичай 3–5 осіб) як групу відновлення. Кожен контакт тримає одну "частку" ключа відновлення — частину головоломки.

**Для відновлення вашого облікового запису:**
1. Ви реєструєте новий пристрій та ініціюєте запит на відновлення
2. Ваші контакти відновлення отримують сповіщення
3. Після налаштовуваної затримки (щоб дати вам час скасувати примусовий запит) порогова кількість контактів (наприклад, 2 з 3) схвалює запит
4. Кожен контакт, що схвалює, надсилає свою частку, зашифровану безпосередньо до вашого нового пристрою
5. Ваш новий пристрій об'єднує частки для відновлення ключа відновлення, який відновлює доступ до ваших зашифрованих даних

**Що сервер може бачити**: Сервер ретранслює зашифровані фрагменти часток між пристроями. Він не може прочитати частки, не може самостійно відновити ключ відновлення та не може обійти вимогу порогу.

### Властивості безпеки груп відновлення

- **Порогова безпека**: Частки нижче порогу не розкривають нічого про секрет — один власник частки не може відновити ваш обліковий запис самостійно
- **Сервер не бере участі в секреті**: Частки шифруються безпосередньо до відкритого ключа вашого нового пристрою; сервер зберігає та ретранслює лише шифротекст
- **Обсяг на хаб**: Відновлення відновлює ваш доступ до одного конкретного хабу. Якщо ви в кількох хабах, кожен хаб має власну групу відновлення
- **Затримка з можливістю скасування**: Ви можете скасувати запит на відновлення протягом періоду затримки — захист від того, щоб хтось ініціював запит на відновлення від вашого імені без вашого відома
- **Верифікація через Signal**: Запити на відновлення верифікуються через Signal, щоб підтвердити, що ви контролюєте обліковий запис Signal, пов'язаний з вашою ідентичністю

### Вибір контактів відновлення

Обирайте людей, яким ви довіряєте, хто:
- Доступний незалежно (не всі в одному місці або організації)
- Сам використовує Signal (необхідно для кроку верифікації)
- Розуміє, що його час від часу проситимуть схвалювати запити на відновлення

Ваші контакти відновлення не отримують доступ до ваших зашифрованих даних, тримаючи частку — вони можуть лише допомогти вам відновитися, коли ви ініціюєте запит.

## Конфіденційність номера телефону волонтера

Коли волонтери отримують дзвінки на особисті телефони, їхні номери стають відомими вашому постачальнику телефонії.

| Сценарій | Номер телефону видимий для |
|----------|----------------------------|
| PSTN дзвінок на телефон волонтера | Постачальник телефонії, телефонний оператор |
| Браузер-до-браузера (WebRTC) | Нікого (аудіо залишається в браузері) |
| Самостійно розміщений Asterisk + SIP телефон | Лише ваш сервер Asterisk |

**Для захисту номерів телефонів волонтерів**: Використовуйте дзвінки через браузер (WebRTC) або надайте SIP-телефони, підключені до самостійно розміщеного Asterisk.

## Нещодавно випущено

Ці покращення вже доступні:

| Функція | Перевага для конфіденційності |
|---------|-------------------------------|
| Управління пристроями | Перегляд та відкликання будь-якого пристрою, з якого ви входили; відкликання запускає зміну ключів, тому вилучений пристрій не може читати новий вміст |
| SAS верифікація пристрою емодзі | Адміністратори можуть верифікувати пристрої особисто за допомогою криптографічного відбитка, що відображається у вигляді 7 емодзі — не може бути підроблено сервером |
| Видалення облікового запису з затримкою | Запит на видалення облікового запису; налаштовувана затримка дозволяє скасувати, якщо запит було зроблено під примусом |
| Екстрене видалення | Співпідтверджене прискорене видалення з мінімальним порогом у 4 години |
| Крипто-знищення при видаленні | Ваші ключі шифрування знищуються в першу чергу, роблячи вміст остаточно нечитабельним до будь-якого видалення з бази даних |
| Групи відновлення (Shamir) | Призначення довірених контактів, які можуть допомогти відновитися, якщо ви втратите всі пристрої — частки нижче порогу не розкривають нічого |
| Розсилки з чесним розкриттям | Адміністратори можуть надсилати масові повідомлення; сервер обробляє відкритий текст тимчасово для доставки (чітко розкрито в інтерфейсі) |
| Гешування підписників | Номери телефонів підписників розсилок зберігаються як гешовані ідентифікатори — жодного списку підписників у відкритому тексті в базі даних |
| Захист ключів Argon2id | Ключі вашого пристрою захищені функцією, стійкою до пам'яті, яка протистоїть атакам грубою силою з GPU та спеціалізованим обладнанням |
| Маршрутизація повідомлень через Signal у першу чергу | Повідомлення автоматично маршрутизуються через Signal, коли доступний, тримаючи вміст поза журналами постачальника SMS |
| Режим лише сповіщень SMS | Отримувачі SMS бачать лише "у вас нове повідомлення" — жодного конфіденційного вмісту в журналах постачальника |
| Стійкість до аналізу трафіку | Розміри подій у реальному часі вирівнюються, щоб спостерігачі не могли відрізнити короткі повідомлення від довгих |
| Відсутність номерів телефонів у відкритому тексті в базі даних | Номери абонентів зберігаються як незворотні геші — ваша база даних ніколи не містить фактичного номера телефону |
| Похабне шифрування з прямою секретністю | Події в реальному часі кожного хабу шифруються ключами, які змінюються кожні 24 години — старі ключі не можуть розшифрувати нові події |
| Криптографія на Rust на всіх платформах | Робочий стіл, iOS та Android використовують одну й ту саму перевірену бібліотеку криптографії Rust — ключі ніколи не потрапляють у код JavaScript, Swift або Kotlin |
| Обмежений доступ до ретранслятора | Ваш WebSocket ретранслятор приймає події лише з вашого сервера — жодна зовнішня сторона не може вставити фальшиві сповіщення |
| Зашифроване зберігання повідомлень | Повідомлення SMS, WhatsApp та Signal зберігаються як шифротекст на вашому сервері |
| Розшифровка на пристрої | Аудіо ніколи не залишає ваш пристрій — обробляється повністю на пристрої за допомогою локального AI |
| Багатофакторний захист ключів | Ваші ключі шифрування захищені вашим PIN-кодом, вашим постачальником ідентифікації та, за бажанням, апаратним ключем безпеки |
| Апаратні ключі безпеки | Фізичні ключі додають третій фактор, який неможливо скомпрометувати віддалено |
| Відтворювані збірки | Перевірте, що розгорнутий код відповідає публічному вихідному коду |
| Зашифрований довідник контактів | Записи контактів, зв'язки та нотатки мають наскрізне шифрування |
