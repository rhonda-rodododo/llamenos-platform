## Архітектура безпеки

Llámenos був розроблений з самого початку для захисту абонентів та волонтерів від добре фінансованих противників — держав, правих груп та приватних розвідувальних фірм. Кожне криптографічне рішення є навмисним, документованим та перевіреним.

**HPKE (RFC 9180) — X25519-HKDF-SHA256-AES256-GCM** — Той самий стандарт гібридного шифрування, що використовується в MLS (Messaging Layer Security) та TLS 1.3. Повністю замінив старіший ECIES (secp256k1). RFC 9180 надає формально визначену, рецензовану конструкцію, а не спеціально зібрану композицію.

**Пряма секретність для нотаток** — Кожна нотатка використовує унікальний випадковий ключ, потім цей ключ HPKE-обгортається окремо для кожного авторизованого читача (волонтера та кожного адміністратора). Компрометація приватного ключа читача не розкриває нічого про нотатки, написані до компрометації. Ієрархія ключів: Персональний ключ користувача (PUK) → items_key → ключ вмісту нотатки, з каскадною лінивою ротацією.

**Подвійне шифрування нотаток** — Кожна нотатка шифрується двічі: один раз HPKE-обгорнута для волонтера, який її написав, і один раз для кожного адміністратора. Обидва можуть розшифрувати незалежно. Ніхто інший — включаючи сервер — не може прочитати відкритий текст.

**57 міток розділення доменів** — Кожна криптографічна операція використовує унікальний рядок контексту (захист Альбрехта). Жодні дві операції не використовують спільний шлях похідних ключів, що запобігає міжпротокольним атакам. Мітки визначені в `packages/protocol/crypto-labels.json` та генеруються в TypeScript, Swift та Kotlin через кодогенерацію. Рядкові літерали ніколи не використовуються в криптографічних контекстах.

**Периферійні ключі Ed25519/X25519** — Користувачі мають ключі на пристрій (а не єдиний ідентифікаційний ключ). Нові пристрої авторизуються через додатковий, геш-ланцюжковий, підписаний Ed25519 ланцюжок підписів (sigchain). Зв'язування пристроїв використовує ефемерні ECDH кімнати надання, які закінчуються через 5 хвилин.

**PIN-захищене зберігання ключів** — Приватні ключі пристрою шифруються з 600 000 ітерацій PBKDF2 + XChaCha20-Poly1305 перед зберіганням. Сирий ключ існує лише в замиканні в пам'яті, обнуляється при блокуванні. Він ніколи не потрапляє в sessionStorage, IndexedDB або на диск у відкритому тексті.

**Рідне безпечне зберігання на платформі** — Робочий стіл: зашифроване сховище Tauri Stronghold. iOS: Keychain iOS. Android: Android Keystore через EncryptedSharedPreferences.

**Лише клієнтська розшифровка** — Розшифровка дзвінків використовує WASM Whisper (`@huggingface/transformers` ONNX runtime), що працює повністю в браузері. Аудіо обробляється локально через конвеєр AudioWorklet ring buffer → Web Worker. Аудіо ніколи не потрапляє на сервер — навіть у зашифрованому вигляді.

**SFrame голосове E2EE** — Зашифровані медіа-канали з використанням SFrame (RFC 9605) з похідними ключів, інтегрованими в спільну криптобібліотеку Rust.

**Спільна криптобібліотека Rust** — Єдина перевірена реалізація в `packages/crypto/`, скомпільована для трьох цілей: рідний (Tauri desktop), WASM (браузер через `@tauri-apps/api`) та UniFFI (iOS XCFramework + Android JNI). Не три окремі реалізації, які можуть розходитися.

**Геш-ланцюжковий журнал аудиту** — Кожен прийнятий дзвінок, створена нотатка, надіслане повідомлення, змінене налаштування та дія адміністратора реєструються з SHA-256 ланцюжком (`previousEntryHash` + `entryHash`) для виявлення втручання. Адміністратори можуть перевірити цілісність ланцюжка.

**Відтворювані збірки** — `Dockerfile.build` з `SOURCE_DATE_EPOCH`, гешовані імена файлів. SLSA походження, SBOM та підписання cosign у кожному релізі. Будь-яка збірка може бути перевірена побайтово з `CHECKSUMS.txt` у GitHub Releases за допомогою `scripts/verify-build.sh`.

## Телефонія — 8 постачальників

**На відміну від більшості платформ, які прив'язують вас до одного постачальника**, Llámenos реалізує інтерфейс `TelephonyAdapter` з 8 повними реалізаціями. Змінюйте постачальника через інтерфейс адміністратора — жодних змін коду, жодного простою.

### Хмарні постачальники (6)

- **Twilio** — Повний WebRTC, програмована голосова зв'язок, SIP транкінг
- **SignalWire** — Twilio-сумісний API, нижча вартість, підтримка WebRTC
- **Vonage** (Nexmo) — Варіант з розташуванням даних у Європі
- **Plivo** — Економічно ефективний, глобальне покриття
- **Telnyx** — Конкурентні ціни, інтеграція з Mission Control Portal
- **Bandwidth** — Корпоративний рівень, надійність операторського рівня США

### Самостійно розміщені SIP (2)

- **Asterisk** — Через ARI (Asterisk REST Interface). Повний контроль дзвінків, IVR, запис.
- **FreeSWITCH** — Через ESL (Event Socket Library). Висока продуктивність, підтримка конференцій.

Обидва використовують базовий клас `SipBridgeAdapter` зі змінною середовища `PBX_TYPE`, що обирає внутрішню реалізацію. Kamailio підтримується як SIP проксі-шар. **Жодні записи дзвінків не залишають ваш сервер.**

### Маршрутизація дзвінків

**Паралельний дзвінок** — Коли абонент телефонує, всі волонтери на зміні, які не зайняті, дзвонять одночасно. Перший, хто відповість, виграє; всі інші негайно припиняються. Жодних пропущених дзвінків через послідовний пошук.

**Розклад на основі змін** — Створюйте повторювані зміни з конкретними днями та часовими діапазонами. Призначайте волонтерів. Система автоматично маршрутизує дзвінки тому, хто на чергуванні. Резервна група дзвінків, якщо розклад не визначено.

**Черга з музикою на утриманні** — Якщо всі волонтери зайняті, абоненти потрапляють у чергу з налаштовуваною музикою на утриманні. Тайм-аут регулюється (30–300 секунд). Переходить на голосову пошту при відсутності відповіді.

**Голосова пошта як резерв** — Абоненти можуть залишити голосове повідомлення (до 5 хвилин). Голосові повідомлення розшифровуються через клієнтський Whisper та шифруються для перегляду адміністратором.

**WebRTC дзвінки в браузері** — Волонтери відповідають на дзвінки безпосередньо в браузері без телефону. Генерація WebRTC токенів для Twilio, SignalWire, Vonage та Plivo.

**Захист від спаму** — Голосова CAPTCHA (рандомізований 4-цифровий ввід клавішами), ковзне віконне обмеження швидкості на номер телефону та чорні списки в реальному часі. Адміністратори вмикають/вимикають кожен контроль незалежно без перезапуску. Власні IVR запити з TTS резервним варіантом.

## Обмін повідомленнями — 5 каналів

Всі канали використовують єдину уніфіковану модель зашифрованих розмов. Кожне вхідне повідомлення HPKE-шифрується при отриманні вебхука; сервер негайно відкидає відкритий текст.

### Signal

Найповніша доступна інтеграція, що не є Twilio. Адаптер Signal включає:

- Повний прийом/передача з підтвердженнями доставки
- Підтвердження прочитання та індикатори набору тексту
- Реакції та гілкування відповідей
- Реєстрація та зв'язування через міст signal-cli-rest-api
- Перевірка довіри до ідентичності та управління номерами безпеки
- Черга повторних спроб з експоненційним відступом
- Відмова на альтернативний транспорт при збої мосту
- Розшифровка голосових повідомлень через клієнтський Whisper
- Моніторинг працездатності з плавною деградацією

### WhatsApp Business

- Meta Cloud API (Graph API v21.0)
- Підтримка шаблонних повідомлень для дотримання 24-годинного вікна
- Медіа-повідомлення: зображення, документи, аудіо, відео
- Перевірка підпису вебхука
- Підтвердження прочитання та статус доставки

### SMS

- Вхідні та вихідні через Twilio, SignalWire, Vonage або Plivo
- Автоматична відповідь з налаштовуваними привітальними повідомленнями для кожної мови
- Підтримка MMS там, де доступно
- Перевірка підпису вебхука для кожного постачальника

### Telegram

- Telegram Bot API
- Підтримка медіа: фото, документи, голосові повідомлення
- Вбудовані клавіатури та розмітка відповідей
- Режим вебхука або опитування

### RCS (Rich Communication Services)

- Google RBM (Rich Business Messaging) API
- Багаті картки, запропоновані дії та каруселі
- Підтвердження доставки та прочитання
- Відмова на SMS там, де RCS недоступний

### Розсилки/масові повідомлення

Черга доставки на основі PostgreSQL для масових повідомлень:

- Обмеження швидкості на канал (дотримується лімітів постачальника)
- Заплановані надсилання з підтримкою часових поясів
- Відстеження статусу на отримувача (в черзі, надіслано, доставлено, не вдалося)
- Логіка повторних спроб з чергою мертвих листів
- Пакетна доставка з налаштовуваними розмірами пакетів
- Панель адміністратора з відображенням прогресу доставки в реальному часі

## Багатоплатформність — три рідні застосунки, одна криптобібліотека

Більшість платформ постачають веб-застосунок з тонкою рідною оболонкою. Llámenos постачає три повністю рідні застосунки, які використовують одну перевірену реалізацію криптографії Rust.

### Робочий стіл (Tauri v2)

- Рідні бінарні файли для Windows, macOS, Linux
- Зашифроване сховище Tauri Stronghold для зберігання ключів
- Рідний системний трей з індикатором вхідного дзвінка
- Автоматичні оновлення через Tauri updater
- Примусове виконання єдиного екземпляра
- Патерн ізоляції + Політика безпеки вмісту
- Всі криптографічні операції проходять через Rust IPC — приватні ключі ніколи не потрапляють у webview
- Режим збірки PLAYWRIGHT_TEST для E2E тестування з імітованим IPC шаром

### iOS (SwiftUI)

- Рідний SwiftUI, iOS 17+ з `@Observable`
- Ключі зберігаються в iOS Keychain
- Криптографія Rust через UniFFI XCFramework (`LlamenosCoreFFI`)
- XCTest + XCUITest для модульного та інтеграційного тестування
- Push-сповіщення через APNs із зашифрованими корисними навантаженнями
- Мультихаб: фонові обробники ніколи не залежать від активного стану хабу

### Android (Kotlin/Compose)

- Рідний Kotlin 2.3 з Jetpack Compose, Material 3
- minSdk 26, AGP 9.1, Gradle 9.4
- Ключі в Android Keystore через EncryptedSharedPreferences
- Криптографія Rust через JNI спільну бібліотеку (файли `.so` з тієї ж криптобібліотеки Rust)
- Впровадження залежностей Hilt + обробка анотацій KSP
- Compose UI тести + Cucumber BDD E2E тести
- Мультихаб: перезавантаження ViewModel на хаб, кешування ключів хабу, маршрутизація WebSocket

### Спільна криптобібліотека Rust

`packages/crypto/` реалізує:

- HPKE (RFC 9180): X25519-HKDF-SHA256-AES256-GCM
- Підписи Ed25519 (BIP-340 Schnorr для сумісності з WebSocket)
- Узгодження ключів X25519
- Похідні ключів PBKDF2 (600K ітерацій)
- HKDF (RFC 5869)
- Автентифіковане шифрування XChaCha20-Poly1305
- SFrame (RFC 9605) голосове E2EE
- MLS (Messaging Layer Security) через OpenMLS — за прапорцем функції `mls`
- Каркас UniFFI для зв'язків iOS/Android
- Компіляція WASM для використання в браузері

## Управління справами

Llámenos не прив'язаний жорстко до якогось конкретного випадку використання. Все працює на основі шаблонів.

**Система сутностей на основі шаблонів** — Адміністратори визначають типи сутностей (контакти, справи, звіти, події), спеціальні поля (текст, число, вибір, прапорець, текстова область, дата, файл) та типи звітів для хабу. Шаблони керують усіма формами та представленнями. Жодних змін коду не потрібно для налаштування нового робочого процесу.

**Власні типи звітів** — Шаблони визначають `reportTypes[]` зі спеціальними полями на тип, `allowCaseConversion` та `mobileOptimized` прапорцями. Типи звітів повністю відрізняються від типів сутностей.

**Сліпий індексний пошук із шифруванням** — Записи зберігаються зашифрованими, але поля з HMAC-індексом дозволяють пошук на стороні сервера без розкриття відкритого тексту. Індекси обмежені хабом і ніколи не перетинають межі хабів.

**Контакти та зв'язки** — Повний довідник контактів з графом зв'язків. Прив'язуйте контакти до справ, подій та доказів. Зв'язки типізовані (наприклад, "є свідком", "є правовим спостерігачем") та налаштовуються на шаблон.

**Управління доказами** — Прикріплюйте файли до справ. Файли шифруються перед завантаженням (HPKE-обгорнуті для кожного авторизованого читача). Ланцюжок зберігання доказів реєструється в аудиторському сліді.

**RBAC** — Контроль доступу на основі ролей: Волонтер (лише власні нотатки), Адміністратор (всі дані), Репортер (лише подання). Власні ролі на шаблон. Адміністратори не можуть бачити нотатки, доступні лише волонтерам.

**Мультихаб** — Одна інсталяція Llámenos обслуговує кілька незалежних хабів (організацій, ліній або випадків використання). Будь-який користувач може бути членом кількох хабів одночасно. Вхідні дзвінки, сповіщення та події ретрансляції з УСІХ хабів-членів завжди активні — не залежать від того, який хаб зараз відображається.

## Автентифікація та управління ключами

**Пари ключів WebSocket** — Користувачі автентифікуються за допомогою сумісних з WebSocket пар ключів Ed25519. Перевірка підпису BIP-340 Schnorr. Жодних паролів, жодних адрес електронної пошти не потрібно для автентифікації.

**Ключі доступу WebAuthn** — Необов'язкова підтримка ключів доступу для входу з кількох пристроїв. Зареєструйте апаратний ключ безпеки або платформну біометрію, потім ввійдіть без введення PIN-коду.

**Sigchain користувача** — Додатковий, геш-ланцюжковий запис авторизації пристроїв. Кожен запис підписаний ключем Ed25519 пристрою, що авторизує. Надає криптографічну історію того, які пристрої авторизовані для якого користувача.

**Каскадна ротація PUK** — Персональний ключ користувача (PUK) → items_key → ключ вмісту нотатки. Коли пристрій деавторизується або користувач змінює свій PIN-код, відповідні ключі обертаються ліниво — перешифровуючи записи лише при доступі до них, а не пакетною операцією.

**Надання пристрою** — Прив'язуйте нові пристрої без розкриття приватного ключа. Відскануйте QR-код або введіть короткий код надання. Використовує ефемерний обмін ключами ECDH. Кімнати надання закінчуються через 5 хвилин.

**Ключі відновлення** — Під час реєстрації генерується ключ відновлення у форматі Base32 (ентропія 128 біт). Обов'язкове завантаження зашифрованої резервної копії перед продовженням. Це єдиний шлях відновлення — без відновлення адміністратором, за задумом.

**Автоматичне блокування** — Менеджер ключів автоматично блокується при простої або коли вкладка браузера прихована. Налаштовувана тривалість простою. Введіть PIN-код повторно для розблокування.

**Модель сесії** — Дворівнева: "автентифікований, але заблокований" (лише токен сесії, представлення тільки для читання) проти "автентифікований та розблокований" (PIN-код введено, повний криптографічний доступ). Токени сесії на 8 годин з попередженнями про тайм-аут простою.

## Інфраструктура реального часу

**WebSocket ретранслятор** — Самостійно розміщений WebSocket ретранслятор (або Nosflare на Cloudflare) для розподілу подій у реальному часі. Весь вміст подій шифрується ключем хабу. Загальні теги (`["t", "llamenos:event"]`) запобігають виведенню метаданих на рівні ретранслятора про типи подій.

**Ключ хабу** — Випадкові 32 байти (`crypto.getRandomValues`), HPKE-обгорнуті індивідуально для кожного члена хабу через `LABEL_HUB_KEY_WRAP`. Обертається при виході члена — колишні члени не можуть розшифрувати майбутні події.

**WebSocket** — Статус дзвінків у реальному часі, присутність волонтерів, оновлення розмов та моніторинг адміністратора через WebSocket. Повторне підключення з експоненційним відступом.

**WebSocket синхронізація в реальному часі** — Ефемерні події kind 20001 для синхронізації стану між пристроями та хабами. Вміст зашифровано; ретранслятор не може розрізнити типи подій.

## Досвід адміністратора та волонтера

**Майстер налаштування** — Покроковий майстер з кількома кроками при першому вході адміністратора. Виберіть канали, налаштуйте постачальників, встановіть назву гарячої лінії. Генерує початкову пару ключів хабу та розподіляє ключ хабу першому адміністратору.

**Контрольний список початку роботи** — Віджет на панелі керування, що відстежує прогрес налаштування: конфігурація каналів, залучення волонтерів, створення змін.

**Моніторинг у реальному часі** — Активні дзвінки, абоненти в черзі, розмови та статус волонтерів оновлюються в реальному часі через WebSocket.

**Палітра команд** — Ctrl+K (або Cmd+K) для миттєвої навігації, пошуку, швидкого створення нотаток та перемикання теми. Команди лише для адміністратора фільтруються за роллю.

**Присутність волонтерів** — Адміністратори бачать кількість онлайн/офлайн/на перерві в реальному часі. Волонтери вмикають перемикач перерви, щоб призупинити вхідні дзвінки без виходу зі зміни.

**Гарячі клавіші** — Натисніть `?` для перегляду всіх гарячих клавіш. Навігація сторінками, відкриття палітри команд, поширені дії без миші.

**Темна/світла теми** — Системна, темна або світла. Зберігається на сесію.

**Експорт даних GDPR** — Експорт нотаток як файлу, що відповідає GDPR (`.enc`). Лише оригінальний автор може розшифрувати.

## Розгортання

### Docker Compose (Один сервер)

- Повний стек: Bun HTTP сервер, PostgreSQL, RustFS (об'єктне сховище), WebSocket ретранслятор
- Додаткові профілі: `--profile signal` (signal-cli сайдкар), `--profile telephony` (Kamailio + CoTURN), `--profile inference` (LLM firehose агент), `--profile monitoring` (Prometheus + Grafana)
- `docker-compose.dev.yml` для локальної розробки з відстеженням файлів
- `docker-compose.production.yml` накладка для посилення безпеки продакшну

### Kubernetes (Helm)

- Продуктовий Helm чарт з налаштовуваними репліками
- Проби здоров'я: `/health/ready` та `/health/live`
- Prometheus ServiceMonitor для збору метрик
- Caddyfile.production з HSTS, CSP та заголовками безпеки
- Ansible попередні перевірки + смоук-тести для валідації перед розгортанням

### Co-op Cloud

- Рецепт для розгортання Co-op Cloud
- Розроблено для робочих кооперативів та громадських організацій, які керують власною інфраструктурою

### Cloudflare Tunnels

- Вхідний трафік через Cloudflare Tunnels — не потрібні відкриті вхідні порти
- Сумісний з самостійно розміщеними серверами за NAT
- Відповідність вимогам ЄС/GDPR щодо розташування даних у поєднанні з VPS, розміщеним в ЄС

### Відповідність GDPR

- Дані зберігаються лише на ваших серверах (або VPS в ЄС)
- Право на видалення: адміністратор може видаляти записи абонентів, нотатки та журнали
- Експорт зашифрованих даних, що відповідає GDPR
- Відсутність сторонньої аналітики або відстеження в самому застосунку

## Signal сайдкар сповіщень

`signal-notifier/` працює на порту 3100 як окремий процес. Він є **з нульовим знанням**: контакти визначаються через HMAC-гешовані ідентифікатори — сайдкар ніколи не зберігає номери телефонів у відкритому тексті. Спільний `SIGNAL_NOTIFIER_BEARER_TOKEN` автентифікує основний застосунок перед сайдкаром.

## Протокол та кодогенерація

Всі типи походять з єдиного джерела істини:

- **Zod схеми** в `packages/protocol/schemas/` визначають всі типи API та дроту
- **Кодогенерація** (`bun run codegen`) генерує структури Swift Codable, класи даних Kotlin `@Serializable` та знімок OpenAPI
- **Криптографічні мітки** в `packages/protocol/crypto-labels.json` (57 констант) генеруються в TypeScript, Swift та Kotlin — жодних сирих рядків у криптокоді
- **i18n кодогенерація** (`bun run i18n:codegen`) генерує iOS `.strings`, Android `strings.xml` та Kotlin `I18n.kt` з файлів локалізації JSON

Це означає, що зміна схеми або протоколу автоматично поширюється на всі три платформи.
