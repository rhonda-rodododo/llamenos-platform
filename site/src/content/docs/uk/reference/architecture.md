Ця сторінка пояснює, як структуровано Llamenos, як дані проходять через систему та де застосовується шифрування.

## Структура репозиторію

Llamenos розділено на три репозиторії, які спільно використовують протокол та криптографічне ядро:

```
llamenos              llamenos-core           llamenos-platform
(Desktop + API)       (Shared Crypto)         (Mobile App)
+--------------+      +--------------+        +--------------+
| Tauri v2     |      | Rust crate   |        | React Native |
| Vite + React |      | - Native lib |        | iOS + Android|
| CF Workers   |      | - WASM pkg   |        | UniFFI bind  |
| Durable Objs |      | - UniFFI     |        |              |
+--------------+      +--------------+        +--------------+
       |                  ^      ^                   |
       |  path dep        |      |    UniFFI         |
       +------------------+      +-------------------+
```

- **llamenos** — Настільний додаток (Tauri v2 із вебпереглядачем Vite + React), бекенд Cloudflare Worker та самостійно розгорнутий бекенд Node.js. Це основний репозиторій.
- **llamenos-core** — Спільний Rust-крейт, який реалізує всі криптографічні операції: ECIES-шифрування конвертів, підписи Schnorr, PBKDF2-виведення ключів, HKDF та XChaCha20-Poly1305. Компілюється в нативний код (для Tauri), WASM (для браузера) та прив'язки UniFFI (для мобільних пристроїв).
- **llamenos-platform** — Мобільний додаток React Native для iOS та Android. Використовує прив'язки UniFFI для виклику того самого Rust-криптокоду.

Усі три платформи реалізують той самий дротовий протокол, визначений у `docs/protocol/PROTOCOL.md`.

## Потік даних

### Вхідний виклик

```
Caller (phone)
    |
    v
Telephony Provider (Twilio / SignalWire / Vonage / Plivo / Asterisk)
    |
    | HTTP webhook
    v
Worker API  -->  CallRouterDO
    |                |
    |                | Checks ShiftManagerDO for on-shift volunteers
    |                | Initiates parallel ring to all available volunteers
    |                v
    |           Telephony Provider (outbound calls to volunteer phones)
    |
    | First volunteer answers
    v
CallRouterDO  -->  Connects caller and volunteer
    |
    | Call ends
    v
Client (volunteer's browser/app)
    |
    | Encrypts note with per-note key
    | Wraps key via ECIES for self + each admin
    v
Worker API  -->  RecordsDO  (stores encrypted note + wrapped keys)
```

### Вхідне повідомлення (SMS / WhatsApp / Signal)

```
Contact (SMS / WhatsApp / Signal)
    |
    | Provider webhook
    v
Worker API  -->  ConversationDO
    |                |
    |                | Encrypts message content immediately
    |                | Wraps symmetric key via ECIES for assigned volunteer + admins
    |                | Discards plaintext
    |                v
    |           WebSocket relay (encrypted hub event notifies online clients)
    |
    v
Client (volunteer's browser/app)
    |
    | Decrypts message with own private key
    | Composes reply, encrypts outbound
    v
Worker API  -->  ConversationDO  -->  Messaging Provider (sends reply)
```

## Durable Objects

Бекенд використовує шість Cloudflare Durable Objects (або їхні еквіваленти PostgreSQL для самостійно розгорнутих інсталяцій):

| Durable Object | Відповідальність |
|---|---|
| **IdentityDO** | Керує ідентичностями волонтерів, публічними ключами, відображуваними іменами та обліковими даними WebAuthn. Обробляє створення та погашення запрошень. |
| **SettingsDO** | Зберігає конфігурацію гарячої лінії: назва, увімкнені канали, облікові дані провайдера, власні поля нотаток, налаштування пом'якшення спаму, прапорці функцій. |
| **RecordsDO** | Зберігає зашифровані нотатки про виклики, зашифровані звіти та метадані вкладень файлів. Обробляє пошук нотаток (по зашифрованих метаданих). |
| **ShiftManagerDO** | Керує повторюваними розкладами змін, групами дзвінків, призначеннями змін волонтерам. Визначає, хто перебуває на зміні в будь-який момент часу. |
| **CallRouterDO** | Оркеструє маршрутизацію викликів у реальному часі: паралельний дзвінок, припинення при першій відповіді, статус перерви, відстеження активних викликів. Генерує відповіді TwiML/провайдера. |
| **ConversationDO** | Керує потоковими розмовами через SMS, WhatsApp та Signal. Обробляє шифрування повідомлень при вхідному потоці, призначення розмов та вихідні відповіді. |

Усі DO доступні як singleton через `idFromName()` та маршрутизуються внутрішньо за допомогою легковагового `DORouter` (узгодження методу + шаблону шляху).

## Матриця шифрування

| Дані | Зашифровано? | Алгоритм | Хто може розшифрувати |
|---|---|---|---|
| Нотатки про виклики | Так (E2EE) | XChaCha20-Poly1305 + ECIES-конверт | Автор нотатки + всі адміністратори |
| Власні поля нотаток | Так (E2EE) | Той самий, що й для нотаток | Автор нотатки + всі адміністратори |
| Звіти | Так (E2EE) | Той самий, що й для нотаток | Автор звіту + всі адміністратори |
| Вкладення до звітів | Так (E2EE) | XChaCha20-Poly1305 (потоковий) | Автор звіту + всі адміністратори |
| Вміст повідомлень | Так (E2EE) | XChaCha20-Poly1305 + ECIES-конверт | Призначений волонтер + всі адміністратори |
| Транскрипти | Так (на зберіганні) | XChaCha20-Poly1305 | Творець транскрипту + всі адміністратори |
| Події хабу (WebSocket) | Так (симетричний) | XChaCha20-Poly1305 із ключем хабу | Усі поточні члени хабу |
| Volunteer nsec | Так (на зберіганні) | PBKDF2 + XChaCha20-Poly1305 (PIN) | Лише волонтер |
| Записи журналу аудиту | Ні (захищено цілісністю) | SHA-256 ланцюг хешів | Адміністратори (читання), система (запис) |
| Номери телефонів абонентів | Ні (лише на стороні сервера) | N/A | Сервер + адміністратори |
| Номери телефонів волонтерів | Зберігається в IdentityDO | N/A | Лише адміністратори |

### Просторова таємниця на рівні нотатки

Кожна нотатка або повідомлення отримує унікальний випадковий симетричний ключ. Цей ключ обгортається через ECIES (епемерний ключ secp256k1 + HKDF + XChaCha20-Poly1305) індивідуально для кожного авторизованого читача. Компрометація ключа однієї нотатки не розкриває нічого про інші нотатки. Не існує довгострокових симетричних ключів для шифрування вмісту.

### Ієрархія ключів

```
Volunteer nsec (BIP-340 Schnorr / secp256k1)
    |
    +-- Виводить npub (x-only public key, 32 bytes)
    |
    +-- Використовується для узгодження ключів ECIES (додає 02 для стисненої форми)
    |
    +-- Підписує події WebSocket (підпис Schnorr)

Hub key (випадкові 32 bytes, НЕ виведені з жодної ідентичності)
    |
    +-- Шифрує події хабу WebSocket у реальному часі
    |
    +-- ECIES-обгорнутий для кожного члена через LABEL_HUB_KEY_WRAP
    |
    +-- Обертається при виході члена

Per-note key (випадкові 32 bytes)
    |
    +-- Шифрує вміст нотатки через XChaCha20-Poly1305
    |
    +-- ECIES-обгорнутий для кожного читача (волонтер + кожен адміністратор)
    |
    +-- Ніколи не повторно використовується між нотатками
```

## Комунікація в реальному часі

Оновлення в реальному часі (нові виклики, повідомлення, зміни змін, присутність) проходять через ретранслятор WebSocket:

- **Самостійне розгортання**: Ретранслятор WebSocket працює поряд із додатком у Docker/Kubernetes
- **Cloudflare**: Nosflare (ретранслятор на базі Cloudflare Workers)

Усі події є епемерними (kind 20001) та зашифровані ключем хабу. Події використовують загальні теги (`["t", "llamenos:event"]`), тому ретранслятор не може розрізняти типи подій. Поле вмісту містить шифротекст XChaCha20-Poly1305.

### Потік подій

```
Client A (дія волонтера)
    |
    | Шифрує вміст події ключем хабу
    | Підписує як подію WebSocket (Schnorr)
    v
WebSocket relay (ретранслятор WebSocket / Nosflare)
    |
    | Транслює підписникам
    v
Client B, C, D...
    |
    | Перевіряє підпис Schnorr
    | Розшифровує вміст ключем хабу
    v
Оновлення локального стану інтерфейсу
```

Ретранслятор бачить зашифровані блоби та дійсні підписи, але не може читати вміст подій або визначати, які дії виконуються.

## Рівні безпеки

### Транспортний рівень

- Усе клієнт-серверне спілкування через HTTPS (TLS 1.3)
- WebSocket-з'єднання з ретранслятором WebSocket через WSS
- Політика безпеки вмісту (CSP) обмежує джерела скриптів, з'єднань та предків фреймів
- Шаблон ізоляції Tauri відокремлює IPC від вебпереглядача

### Прикладний рівень

- Автентифікація через ключові пари WebSocket (підписи BIP-340 Schnorr)
- Сеансові токени WebAuthn для зручності роботи з кількома пристроями
- Керування доступом на основі ролей (абонент, волонтер, репортер, адміністратор)
- Усі 25 криптографічних констант розділення доменів, визначені в `crypto-labels.ts`, запобігають міжпротокольним атакам

### Шифрування на зберіганні

- Нотатки про виклики, звіти, повідомлення та транскрипти шифруються перед зберіганням
- Секретні ключі волонтерів шифруються ключами, виведеними з PIN (PBKDF2)
- Tauri Stronghold забезпечує зашифроване сховище настільних даних
- Цілісність журналу аудиту захищено через SHA-256 ланцюг хешів

### Верифікація збірки

- Відтворювані збірки через `Dockerfile.build` із `SOURCE_DATE_EPOCH`
- Хешовані імена файлів для ресурсів фронтенду
- `CHECKSUMS.txt` публікується разом із GitHub Releases
- Атестації походження SLSA
- Скрипт верифікації: `scripts/verify-build.sh`

|---|---|---|---|

| Push-сповіщення | Нативні ОС (Tauri notification) | Нативні ОС (FCM/APNS) | Сповіщення браузера |
