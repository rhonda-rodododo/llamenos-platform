این صفحه توضیح می‌دهد که Llámenos چگونه ساختار یافته است، داده‌ها چگونه از سیستم عبور می‌کنند و رمزنگاری کجا اعمال می‌شود.

## ساختار مخزن

Llámenos در سه مخزن تقسیم شده است که یک پروتکل و هسته رمزنگاری مشترک دارند:

```
llamenos              llamenos-core           llamenos-platform
(Desktop + API)       (Shared Crypto)         (Mobile App)
+--------------+      +--------------+        +--------------+
| Tauri v2     |      | Rust crate   |        | React Native |
| Vite + React |      | - Native lib |        | iOS + Android|
| CF Workers   |      | - WASM pkg   |        | UniFFI bind  |
| Durable Objs |      | - UniFFI     |        |              |
+--------------+      +--------------+        +--------------+
       |                  ^      ^                   |
       |  path dep        |      |    UniFFI         |
       +------------------+      +-------------------+
```

- **llamenos** — برنامه دسکتاپ (Tauri v2 با یک webview Vite + React)، بک‌اند Cloudflare Worker و بک‌اند Node.js میزبانی شخصی. این مخزن اصلی است.
- **llamenos-core** — یک crate Rust مشترک که همه عملیات رمزنگاری را پیاده‌سازی می‌کند: رمزنگاری envelope ECIES، امضاهای Schnorr، استخراج کلید PBKDF2، HKDF و XChaCha20-Poly1305. به کد بومی (برای Tauri)، WASM (برای مرورگر) و bindingهای UniFFI (برای موبایل) کامپایل می‌شود.
- **llamenos-platform** — برنامه موبایل React Native برای iOS و Android. از bindingهای UniFFI برای فراخوانی به همان کد Rust رمزنگاری استفاده می‌کند.

هر سه پلتفرم پروتکل wire یکسانی را که در `docs/protocol/PROTOCOL.md` تعریف شده پیاده‌سازی می‌کنند.

## جریان داده

### تماس ورودی

```
تماس‌گیرنده (تلفن)
    |
    v
ارائه‌دهنده تلفنی (Twilio / SignalWire / Vonage / Plivo / Asterisk)
    |
    | HTTP webhook
    v
Worker API  -->  CallRouterDO
    |                |
    |                | ShiftManagerDO را برای داوطلبان شیفت فعال بررسی می‌کند
    |                | زنگ همزمان به همه داوطلبان موجود را آغاز می‌کند
    |                v
    |           ارائه‌دهنده تلفنی (تماس‌های خروجی به تلفن‌های داوطلب)
    |
    | اولین داوطلب پاسخ می‌دهد
    v
CallRouterDO  -->  تماس‌گیرنده و داوطلب را متصل می‌کند
    |
    | تماس پایان می‌یابد
    v
کلاینت (مرورگر/برنامه داوطلب)
    |
    | یادداشت را با کلید هر یادداشت رمزنگاری می‌کند
    | کلید را از طریق ECIES برای خود + هر مدیر wrap می‌کند
    v
Worker API  -->  RecordsDO  (یادداشت رمزنگاری شده + کلیدهای wrapped را ذخیره می‌کند)
```

### پیام ورودی (SMS / WhatsApp / Signal)

```
مخاطب (SMS / WhatsApp / Signal)
    |
    | Provider webhook
    v
Worker API  -->  ConversationDO
    |                |
    |                | محتوای پیام را بلافاصله رمزنگاری می‌کند
    |                | کلید متقارن را از طریق ECIES برای داوطلب تعیین‌شده + مدیران wrap می‌کند
    |                | متن ساده را دور می‌ریزد
    |                v
    |           رله WebSocket (رویداد hub رمزنگاری شده کلاینت‌های آنلاین را مطلع می‌کند)
    |
    v
کلاینت (مرورگر/برنامه داوطلب)
    |
    | پیام را با کلید خصوصی خود رمزگشایی می‌کند
    | پاسخ را ترکیب می‌کند، خروجی را رمزنگاری می‌کند
    v
Worker API  -->  ConversationDO  -->  ارائه‌دهنده پیام‌رسانی (پاسخ را ارسال می‌کند)
```

## Durable Objects

بک‌اند از شش Cloudflare Durable Object (یا معادل‌های PostgreSQL آنها برای استقرارهای میزبانی شخصی) استفاده می‌کند:

| Durable Object | مسئولیت |
|---|---|
| **IdentityDO** | مدیریت هویت‌های داوطلب، کلیدهای عمومی، نام‌های نمایشی و اعتبارنامه‌های WebAuthn. ایجاد و استفاده از دعوت‌نامه‌ها را مدیریت می‌کند. |
| **SettingsDO** | پیکربندی خط تلفن را ذخیره می‌کند: نام، کانال‌های فعال، اعتبارنامه‌های ارائه‌دهنده، فیلدهای یادداشت سفارشی، تنظیمات کاهش هرزنامه، پرچم‌های ویژگی. |
| **RecordsDO** | یادداشت‌های تماس رمزنگاری شده، گزارش‌های رمزنگاری شده و متاداده پیوست فایل را ذخیره می‌کند. جستجوی یادداشت (روی متاداده رمزنگاری شده) را مدیریت می‌کند. |
| **ShiftManagerDO** | برنامه‌های شیفت تکراری، گروه‌های زنگ و تخصیص‌های شیفت داوطلب را مدیریت می‌کند. تعیین می‌کند چه کسی در هر زمان معینی در شیفت است. |
| **CallRouterDO** | مسیریابی تماس بلادرنگ را هماهنگ می‌کند: زنگ همزمان، خاتمه اولین پاسخ، وضعیت استراحت، ردیابی تماس فعال. پاسخ‌های TwiML/ارائه‌دهنده را تولید می‌کند. |
| **ConversationDO** | مکالمات پیام‌رسانی رشته‌ای در SMS، WhatsApp و Signal را مدیریت می‌کند. رمزنگاری پیام در ingest، تخصیص مکالمه و پاسخ‌های خروجی را مدیریت می‌کند. |

همه DOها از طریق `idFromName()` به عنوان singleton دسترسی پیدا می‌کنند و از طریق یک `DORouter` سبک (تطبیق روش + الگوی مسیر) به صورت داخلی مسیریابی می‌شوند.

## ماتریس رمزنگاری

| داده | رمزنگاری شده؟ | الگوریتم | چه کسی می‌تواند رمزگشایی کند |
|---|---|---|---|
| یادداشت‌های تماس | بله (E2EE) | XChaCha20-Poly1305 + envelope ECIES | نویسنده یادداشت + همه مدیران |
| فیلدهای سفارشی یادداشت | بله (E2EE) | همانند یادداشت‌ها | نویسنده یادداشت + همه مدیران |
| گزارش‌ها | بله (E2EE) | همانند یادداشت‌ها | نویسنده گزارش + همه مدیران |
| پیوست‌های گزارش | بله (E2EE) | XChaCha20-Poly1305 (استریم) | نویسنده گزارش + همه مدیران |
| محتوای پیام | بله (E2EE) | XChaCha20-Poly1305 + envelope ECIES | داوطلب تعیین‌شده + همه مدیران |
| رونویسی‌ها | بله (در حالت استراحت) | XChaCha20-Poly1305 | سازنده رونویسی + همه مدیران |
| رویدادهای hub (WebSocket) | بله (متقارن) | XChaCha20-Poly1305 با کلید hub | همه اعضای فعلی hub |
| nsec داوطلب | بله (در حالت استراحت) | PBKDF2 + XChaCha20-Poly1305 (PIN) | فقط داوطلب |
| ورودی‌های گزارش حسابرسی | خیر (محافظت‌شده از یکپارچگی) | زنجیره هش SHA-256 | مدیران (خواندن)، سیستم (نوشتن) |
| شماره تلفن تماس‌گیرندگان | خیر (فقط سمت سرور) | N/A | سرور + مدیران |
| شماره تلفن داوطلبان | در IdentityDO ذخیره شده | N/A | فقط مدیران |

### محرمانگی رو به جلو هر یادداشت

هر یادداشت یا پیام یک کلید متقارن تصادفی منحصربه‌فرد دریافت می‌کند. آن کلید از طریق ECIES (کلید ephemeral secp256k1 + HKDF + XChaCha20-Poly1305) به صورت فردی برای هر خواننده مجاز wrap می‌شود. به خطر افتادن کلید یک یادداشت هیچ چیزی درباره یادداشت‌های دیگر فاش نمی‌کند. هیچ کلید متقارن بلندمدتی برای رمزنگاری محتوا وجود ندارد.

### سلسله مراتب کلید

```
nsec داوطلب (BIP-340 Schnorr / secp256k1)
    |
    +-- npub را استخراج می‌کند (کلید عمومی x-only، ۳۲ بایت)
    |
    +-- برای توافق کلید ECIES استفاده می‌شود (۰۲ را برای فرم فشرده پیشوند می‌دهد)
    |
    +-- رویدادهای WebSocket را امضا می‌کند (امضای Schnorr)

کلید hub (۳۲ بایت تصادفی، از هیچ هویتی استخراج نمی‌شود)
    |
    +-- رویدادهای hub WebSocket بلادرنگ را رمزنگاری می‌کند
    |
    +-- از طریق LABEL_HUB_KEY_WRAP برای هر عضو با ECIES wrap می‌شود
    |
    +-- با خروج عضو چرخانده می‌شود

کلید هر یادداشت (۳۲ بایت تصادفی)
    |
    +-- محتوای یادداشت را از طریق XChaCha20-Poly1305 رمزنگاری می‌کند
    |
    +-- از طریق ECIES برای هر خواننده (داوطلب + هر مدیر) wrap می‌شود
    |
    +-- هرگز در یادداشت‌ها استفاده مجدد نمی‌شود
```

## ارتباط بلادرنگ

به‌روزرسانی‌های بلادرنگ (تماس‌های جدید، پیام‌ها، تغییرات شیفت، حضور) از طریق یک رله WebSocket جریان می‌یابند:

- **میزبانی شخصی**: رله WebSocket در کنار برنامه در Docker/Kubernetes اجرا می‌شود
- **Cloudflare**: Nosflare (رله مبتنی بر Cloudflare Workers)

همه رویدادها ephemeral (kind 20001) هستند و با کلید hub رمزنگاری می‌شوند. رویدادها از تگ‌های عمومی (`["t", "llamenos:event"]`) استفاده می‌کنند تا رله نتواند انواع رویداد را تشخیص دهد. فیلد محتوا شامل ciphertext XChaCha20-Poly1305 است.

### جریان رویداد

```
کلاینت A (عمل داوطلب)
    |
    | محتوای رویداد را با کلید hub رمزنگاری می‌کند
    | به عنوان رویداد WebSocket امضا می‌کند (Schnorr)
    v
رله WebSocket (رله WebSocket / Nosflare)
    |
    | به مشترکان پخش می‌کند
    v
کلاینت B، C، D...
    |
    | امضای Schnorr را تأیید می‌کند
    | محتوا را با کلید hub رمزگشایی می‌کند
    v
وضعیت UI محلی را به‌روزرسانی می‌کند
```

رله blobهای رمزنگاری شده و امضاهای معتبر را می‌بیند اما نمی‌تواند محتوای رویداد را بخواند یا تعیین کند چه عملیاتی در حال انجام است.

## لایه‌های امنیتی

### لایه انتقال

- همه ارتباطات کلاینت-سرور از طریق HTTPS (TLS 1.3)
- اتصالات WebSocket به رله WebSocket از طریق WSS
- Content Security Policy (CSP) منابع اسکریپت، اتصالات و اجداد فریم را محدود می‌کند
- الگوی جداسازی Tauri IPC را از webview جدا می‌کند

### لایه برنامه

- احراز هویت از طریق جفت‌کلیدهای WebSocket (امضاهای BIP-340 Schnorr)
- توکن‌های نشست WebAuthn برای راحتی چند دستگاهی
- کنترل دسترسی مبتنی بر نقش (تماس‌گیرنده، داوطلب، گزارش‌دهنده، مدیر)
- همه ۲۵ ثابت جداسازی دامنه رمزنگاری تعریف شده در `crypto-labels.ts` از حملات cross-protocol جلوگیری می‌کنند

### رمزنگاری در حالت استراحت

- یادداشت‌های تماس، گزارش‌ها، پیام‌ها و رونویسی‌ها قبل از ذخیره‌سازی رمزنگاری می‌شوند
- کلیدهای مخفی داوطلب با کلیدهای مشتق از PIN (PBKDF2) رمزنگاری می‌شوند
- Tauri Stronghold ذخیره‌سازی vault رمزنگاری شده روی دسکتاپ فراهم می‌کند
- یکپارچگی گزارش حسابرسی از طریق زنجیره هش SHA-256 محافظت می‌شود

### تأیید ساخت

- ساخت‌های قابل بازتولید از طریق `Dockerfile.build` با `SOURCE_DATE_EPOCH`
- نام فایل‌های hash شده محتوا برای دارایی‌های فرانت‌اند
- `CHECKSUMS.txt` همراه با GitHub Releases منتشر می‌شود
- گواهی‌های SLSA provenance
- اسکریپت تأیید: `scripts/verify-build.sh`

## تفاوت‌های پلتفرم

| ویژگی | دسکتاپ (Tauri) | موبایل (React Native) | مرورگر (Cloudflare) |
|---|---|---|---|
| بک‌اند رمزنگاری | Rust بومی (از طریق IPC) | Rust بومی (از طریق UniFFI) | WASM (llamenos-core) |
| ذخیره‌سازی کلید | Tauri Stronghold (رمزنگاری شده) | Secure Enclave / Keystore | localStorage مرورگر (رمزنگاری شده با PIN) |
| رونویسی | Whisper سمت کلاینت (WASM) | در دسترس نیست | Whisper سمت کلاینت (WASM) |
| به‌روزرسانی خودکار | Tauri updater | App Store / Play Store | خودکار (CF Workers) |
| اعلان‌های فشاری | بومی سیستم‌عامل (اعلان Tauri) | بومی سیستم‌عامل (FCM/APNS) | اعلان‌های مرورگر |
| پشتیبانی آفلاین | محدود (نیاز به API) | محدود (نیاز به API) | محدود (نیاز به API) |
